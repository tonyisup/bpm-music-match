## Problem Statement

During workouts, movement cadence changes between running, squats, jump rope, and other exercises. Existing workout-music tools tend to assume a steady running pace, automatic sensor input, or a browse-first music flow.

This product lets the user manually establish the current movement cadence by tapping a large mobile control. Each tap produces immediate rhythmic feedback. When tapping stops and the cadence is stable, the app locks the BPM, continues the rhythm briefly, and crossfades it into a matching song.

The first prototype is a mobile web app for Tony's personal use. Tony's normal music source is YouTube Music, but the first prototype deliberately uses one controlled, license-cleared audio track. This moves the actual product boundary: the app owns both the percussion and song audio graphs, so it can test a true overlapping crossfade rather than weakening the interaction to fit YouTube's iframe and policy constraints.

## What Makes This Cool

The product is not a BPM search box. The defining moment is that the song feels as if it was hidden inside the user's taps all along.

Tony described the desired interaction as:

> "a metronome type sound acknowledging the bpm, when I stop tapping to confirm that pace it then cross fades into a song that matches"

A strong handoff has four properties:

1. **Immediate acknowledgment:** every tap produces a musical percussion hit and visual pulse.
2. **Trustworthy lock:** the app locks only when enough taps agree; one late tap does not trigger a false transition.
3. **Musical entry:** the song's target downbeat is phase-aligned to the continued tap rhythm.
4. **True crossfade:** the local percussion and music overlap through independently controlled Web Audio gain nodes, with no dead air.

## Decision: Control the Audio Before Integrating a Provider

The original design targeted a YouTube iframe. Adversarial review found that this would weaken or endanger the core interaction:

- IFrame playback timing and volume control are approximate.
- Mobile delayed autoplay may require another gesture.
- YouTube does not expose audio to the Web Audio graph.
- YouTube developer policy prohibits separating/modifying audiovisual components or applying alternate audio tracks. Overlapping generated percussion with YouTube audio is not safe to assume compliant.

Tony chose to preserve the true crossfade with controlled audio. Therefore:

- **First experiential prototype:** one controlled, license-cleared track routed through Web Audio.
- **Later provider work:** evaluate YouTube as a non-overlapping baton pass, obtain qualified policy guidance, or assess another provider with an official mixing-capable API.
- YouTube integration is not an implementation dependency for this design.

## Constraints

### Product constraints

- Target surface: mobile web browser.
- Approach C uses exactly **one track and one annotated target cadence**.
- The acceptance run deliberately taps near that track's BPM.
- There are no accounts, backend, search, playlists, generalized matching engine, automatic BPM analysis, workout plans, provider login, or PWA installation in the first milestone.
- A tap outside the one track's accepted BPM window produces a clear “No match in this prototype” result.
- If one controlled crossfade cannot feel convincing, catalog breadth is not justified.

### Audio constraints

- Both the percussion and track must be routed through the same Web Audio `AudioContext` using separate `GainNode` paths.
- The track must be decoded and ready before tapping begins. Loading or decoding during the handoff is not allowed.
- The track must be legally usable in the prototype:
  - either a bundled public-domain/CC0/explicitly licensed asset with attribution stored in the repository,
  - or a user-selected local file that is decoded in-browser and never uploaded or persisted by the app.
- A commercial copyrighted track must not be committed to or deployed from the repository without redistribution rights.
- The first tap resumes the `AudioContext` under a direct user gesture.
- Backgrounding, interruption, or `AudioContext` suspension stops all scheduled audio and returns the app to ready.
- Exact sample scheduling is available inside Web Audio, but acoustic output still includes device/audio-stack latency. Acceptance therefore combines deterministic control-plane checks with Tony's perceptual verdict.

### Browser constraints

- The exact acceptance phone, OS, and browser must be recorded.
- The prototype must be tested from its deployed HTTPS origin, not only desktop emulation.
- A local-file input path must be tested on the acceptance browser if the chosen asset is not bundled.
- Audio decode failure, unsupported format, context-resume failure, and interrupted playback must fail loudly with a single recovery action.

## Premises

1. The first product is a personal mobile-web workout tool, not a general music discovery platform.
2. The defining experience is the true sonic crossfade, not a song-results list or provider integration.
3. The first prototype proves one handoff with one controlled track.
4. The prototype accepts taps only within ±3 BPM of that track's 1:1 BPM.
5. Half-time and double-time logic is deferred. Later, each track must explicitly declare rhythmic suitability; mathematical equivalence alone is insufficient.
6. The first prototype handles one transition at a time. Continuous sensing and workout programming are deferred.
7. If one controlled handoff cannot feel good on the real acceptance device after one defined tuning cycle, stop and reassess rather than adding tracks.

## Approaches Considered

### Approach A: YouTube Handoff

Use one visible YouTube player and fade percussion out before YouTube becomes audible.

**Reason not chosen:** This preserves Tony's provider but turns the defining crossfade into a non-overlapping baton pass and leaves mobile autoplay/timing risk.

### Approach B: Curated Movement DJ

Build a reusable catalog, matching engine, installable PWA shell, and 8–12 tracks.

**Reason not chosen:** It spends time on selection architecture before the core transition has been proven.

### Approach C: One Perfect Controlled-Audio Crossfade — Chosen

Use one controlled, license-cleared track. Route both track and percussion through Web Audio so the app owns timing, phase, and gain curves.

**Effort:** One focused weekend after the track and acceptance device are selected.

**Primary risk:** Whether the interaction feels musically inevitable during real movement, not whether an external provider permits playback.

## Recommended Approach

Proceed with **Approach C: One Perfect Controlled-Audio Crossfade** through two gates.

### Gate 1: Mobile audio-control spike

Before building the tap estimator:

1. Deploy a static HTTPS page.
2. Load and decode the chosen track before enabling the tap surface.
3. On the exact acceptance phone/browser, resume the `AudioContext` from a tap.
4. Schedule a percussion sound and a track segment through independent gain nodes several seconds after that gesture.
5. Apply the intended equal-power crossfade curve.
6. Record whether scheduled playback, gain automation, and interruption behavior work from the deployed origin.

**Pass conditions:**

- Track decodes successfully in all three fresh-load trials.
- `AudioContext.resume()` succeeds from the direct tap gesture in all three trials.
- Both gain paths play and the scheduled crossfade completes in all three trials.
- No second playback gesture is required after the initial tap.
- Backgrounding stops the run and returns to ready rather than resuming stale audio.

**Stop conditions:**

- Any repeated format/decode incompatibility that cannot be removed by choosing a web-safe asset.
- The acceptance browser repeatedly suspends scheduled playback after the initial gesture.
- Independent gain automation cannot be heard reliably on the acceptance device.

### Gate 2: One-track vertical slice

Only after Gate 1 passes, implement the full interaction below.

## Interaction Sequence

1. **Loading**
   - Load the bundled licensed track or prompt for one local file.
   - Decode it into an `AudioBuffer`.
   - Validate that the configured start/downbeat positions fit inside the buffer.
   - On success, enter ready. On failure, show **Choose another file** or **Retry** according to source mode.

2. **Ready**
   - Show one large tap surface.
   - Show: “Tap your movement. Stop when the pace feels right. The rhythm will crossfade into the loaded song.”
   - Display the loaded track label and target BPM.

3. **Tracking**
   - On the first tap, resume the `AudioContext`.
   - Map `performance.now()` to `AudioContext.currentTime` for scheduling.
   - Record each tap timestamp.
   - Play a short musical percussion hit and show a visual pulse.
   - Estimate BPM from the latest interval window.

4. **Armed**
   - Enter only after enough stable intervals exist.
   - Continue accepting taps and updating the estimate.
   - Start a phase-locked rolling percussion scheduler as soon as the estimator becomes armed. Keep at most two predicted beats scheduled ahead.
   - Register every scheduled one-shot percussion source in `activePercussionSources` with its generation and scheduled time.
   - When a physical tap arrives within ±60 ms of a predicted hit, count the scheduled hit as its audible acknowledgment, do not create a second hit, and re-anchor only future beats to the physical tap.
   - When a physical tap falls outside ±60 ms, play one immediate hit, cancel all not-yet-started predicted hits, and rebuild the future grid from that tap.
   - Show tentative BPM and “Stop tapping to lock.”

5. **Locked**
   - Enter only when the tempo-relative silence timeout fires while armed.
   - Freeze `estimatedBpm` for display and matching.
   - If BPM is outside the fixed ±3 BPM window, show “No match in this prototype.”
   - If BPM is in range, set `handoffBpm = configuredTrackBpm` and choose the next safe predicted beat on the estimated grid as the quantization boundary.
   - Cancel predicted estimated-tempo hits after that boundary. The boundary hit becomes handoff beat 1; all later beats use `handoffBpm`.

6. **Handoff**
   - Assume 4/4 for the first prototype.
   - The handoff lasts eight beats at `handoffBpm`.
   - Continue local percussion through handoff beat 8. The rolling armed-state scheduler ensures there is no silent rhythmic gap between the final physical tap and handoff beat 1.
   - Start the track buffer at handoff beat 1 using an offset four beats before the configured target-entry downbeat.
   - Keep track gain at zero during beats 1–4 while percussion confirms the cadence.
   - At beat 5, the track reaches `targetEntryDownbeatSeconds`.
   - During beats 5–8, apply an equal-power crossfade: track gain rises from 0 to 1 while percussion gain falls from 1 to 0.
   - At beat 9, stop percussion scheduling and continue the song at full target gain.

7. **Playing**
   - Show locked BPM and track identity.
   - Show both the measured cadence and the track tempo if they differ.
   - A new tap invokes the idempotent click-free teardown contract, then starts a fresh tracking generation.

## Timing Model

### Tap-derived phase and tempo quantization

Let:

```text
estimatedBpm = stable measured user cadence
handoffBpm = configuredTrackBpm
estimatedBeatDurationSeconds = 60 / estimatedBpm
handoffBeatDurationSeconds = 60 / handoffBpm
lastTapAudioTime = mapped AudioContext time of the last accepted tap
lookaheadSeconds = 0.10
```

While armed, the rolling scheduler emits predicted hits on the estimated grid. When lock occurs at `audioNow`, choose the first future predicted beat that preserves the measured phase and leaves scheduling headroom:

```text
n = ceil(
  (audioNow + lookaheadSeconds - lastTapAudioTime)
  / estimatedBeatDurationSeconds
)
handoffBeat1AudioTime =
  lastTapAudioTime + n * estimatedBeatDurationSeconds
```

No beat is actually omitted: the armed-state scheduler continues predicted percussion while silence detection runs. At `handoffBeat1AudioTime`, the period deliberately quantizes from `estimatedBpm` to `handoffBpm`. Beat 1 occurs on the user's estimated phase; beats 2 onward use the track period.

The ±3 BPM acceptance window is an initial hypothesis. Real-device trials must include taps near both edges. If the period snap is perceptible or feels mechanical at either edge, narrow the window before replication. Time-stretching is explicitly out of scope.

### Track phase

For the first prototype:

```text
beatsPerBar = 4
leadInBeats = 4
beatDurationSeconds = 60 / handoffBpm
crossfadeDurationSeconds = 4 * beatDurationSeconds
trackStartOffsetSeconds =
  targetEntryDownbeatSeconds - leadInBeats * beatDurationSeconds
```

Required invariant:

```text
0 <= trackStartOffsetSeconds
targetEntryDownbeatSeconds + crossfadeDurationSeconds
  + postCrossfadeTailSeconds <= trackDurationSeconds
```

`postCrossfadeTailSeconds` defaults to 2.0 seconds so the prototype cannot enter playing and end immediately. Schedule the track `AudioBufferSourceNode` at `handoffBeat1AudioTime` with `trackStartOffsetSeconds`. Beats 1–4 are an **inaudible track pre-roll**. The configured target downbeat reaches the output at handoff beat 5 by construction.

### Crossfade curve

Use equal-power gain curves over beats 5–8:

```text
musicGain(x) = sin(x * π / 2)
percussionGain(x) = cos(x * π / 2)
for x from 0 to 1
```

Implement with `AudioParam.setValueCurveAtTime()` using the same start time and duration for both gain nodes. Do not use timer-driven DOM callbacks for audio gain automation.

### Level calibration and headroom

Equal-power coefficients preserve perceived energy between already balanced sources; they do not prevent clipping or balance a mastered song against a percussion transient. Use this graph:

```text
percussion source -> percussion trim -> percussion crossfade gain \
                                                               -> master gain -> destination
track source      -> track trim      -> track crossfade gain      /
```

Initial fixed values for the one-track spike:

```text
trackTrimGain = 0.70
percussionTrimGain = manually tuned, initial hypothesis 0.35
masterGain = 0.80
```

The offline render must remain below 0.98 absolute peak. The real-device gate must include an audible-clipping check. A normalization scanner or limiter is intentionally out of scope.

## Initial Cadence Hypotheses

These are testable starting values, not permanent constants:

- Timestamp window: latest eight taps, yielding up to seven intervals.
- Interval median: median of the current window.
- Outlier rule: reject an interval more than 20% away from the median.
- Minimum stability: at least four valid intervals.
- Stability metric: coefficient of variation of valid intervals ≤5%.
- Estimated BPM: `60000 / medianIntervalMs`.
- Silence timeout: `clamp(1.5 × medianIntervalMs, 900 ms, 1800 ms)`.
- Fixed-track acceptance: estimated BPM within ±3 BPM of the configured 1:1 track BPM.
- If the estimator is not armed when silence occurs, no lock and no handoff occur.

## Architecture Boundary

Approach C has four small units:

1. **Track loader:** loads/decodes one bundled or local audio file and validates metadata bounds.
2. **Tap estimator:** pure timestamps in; estimated BPM, stability, and armed/not-armed out.
3. **Transition reducer/controller:** explicit state/event transitions, generation ID, scheduling, cancellation, and cleanup.
4. **Raw Web Audio engine:** owns the single shared native `AudioContext`, every one-shot percussion source, the track buffer source, trim nodes, crossfade nodes, master gain, and equal-power automation.

There is no Tone.js dependency, second audio context, provider adapter, catalog, generalized matcher, audio analysis pipeline, or backend.

## Transition Contract

Every new tracking session increments a `generationId`. Application-owned timers and callbacks capture that ID. Every track or percussion `AudioBufferSourceNode` also captures its creation generation and an `intentionallyStopping` flag in application metadata.

Because Web Audio source nodes are one-shot, each percussion hit and each handoff creates fresh nodes. `activePercussionSources` owns every scheduled or sounding percussion node until its `onended` cleanup. `activeTrackSource` owns the current song node.

All cancellation paths call one idempotent `teardownAudio(reason, nextState)` contract:

1. Increment/invalidate the generation before scheduling replacement work.
2. Cancel pending lock and transition timers.
3. Mark owned sources as intentionally stopping.
4. At `audioNow`, call `cancelAndHoldAtTime()` on gain parameters where supported; otherwise cancel scheduled values and set the engine's last computed envelope value.
5. Apply a 20 ms linear ramp to zero on the affected bus to avoid clicks.
6. Call `stop(audioNow + 0.025)` on the track and every future/sounding percussion source in the registry.
7. Ignore `onended` as a natural completion unless its captured generation is still active and `intentionallyStopping` is false.
8. Disconnect and remove each source from its registry inside `onended`, after the cancellation ramp has completed. Teardown never disconnects a sounding source synchronously.

Calling teardown twice is a no-op after the first ownership clear. Cancellation tests cover before track start, during inaudible pre-roll, during crossfade, during playing, and simultaneous visibility/context interruption.

| Current state | Event | Next state | Required action |
|---|---|---|---|
| loading | decode success | ready | Store AudioBuffer and validated metadata |
| loading | decode failure | load-error | Show Retry or Choose another file |
| load-error | retry/new file | loading | Clear prior buffer/error and decode |
| ready | tap | tracking | Increment generation; resume AudioContext; record tap |
| tracking | stable intervals | armed | Show tentative BPM; start rolling predicted-percussion scheduler |
| tracking | silence while unstable | ready | Clear taps; no handoff |
| armed | tap | armed | Reconcile/cancel predicted hit; update estimate; rebuild future grid; restart silence timer |
| armed | silence timeout | locked | Freeze BPM and cancel tap timer |
| locked | BPM outside window | no-match | Show explicit no-match result |
| no-match | acknowledge/reset | ready | Clear locked BPM and taps |
| locked | BPM inside window | handoff | Quantize at next predicted beat; create source/gains; schedule eight-beat transition |
| handoff | new tap | tracking | Run idempotent teardown; record tap in the new generation |
| handoff | natural source end before required tail | audio-error | Run teardown and show Reset |
| handoff | eight-beat transition completes | playing | Stop percussion; retain active track source |
| playing | new tap | tracking | Run idempotent teardown; record tap in the new generation |
| playing | natural track end | ready | `onended` clears active source and shows Ready |
| audio-error | reset | ready | Clear nodes, schedules, and error |
| any active state | document hidden or AudioContext suspended | ready | Stop/disconnect all audio and require explicit restart |
| any active state | reset | ready | Run idempotent teardown and enter ready |

Recovery actions are singular:

- Decode/format failure: **Choose another file** or **Retry** for bundled mode.
- No BPM match: **Reset**.
- Audio scheduling/source failure: **Reset**.
- Background interruption: automatic stop followed by explicit **Tap to restart**.

## Success Criteria

### Gate 1: Mobile audio control

- Three fresh-load trials on the exact acceptance device and deployed HTTPS origin.
- Chosen track decodes successfully in all three.
- `AudioContext.resume()` succeeds from the first direct tap in all three.
- Delayed, scheduled percussion and music playback require no second gesture in all three.
- Equal-power automation completes through both gain paths in all three.
- Backgrounding cancels audio and returns to ready in all three.

### Cadence detection

- After eight steady taps at 60, 90, 120, 160, and 180 BPM, estimated BPM is within ±2 BPM in deterministic tests.
- One interval delayed by up to 20% does not produce an immediate false lock.
- Fewer than five taps/four valid intervals cannot arm the transition.
- The stop threshold follows the documented formula and clamps.

### Control-plane timing

- From the last physical tap through handoff beat 1, there is no missing or doubled percussion hit outside the ±60 ms reconciliation tolerance.
- `estimatedBpm` and `handoffBpm` are both observable, and the period snap occurs only at handoff beat 1.
- Scheduled handoff beat 1 preserves the tap-derived phase formula.
- Track start offset satisfies the documented invariant.
- Track target downbeat is scheduled at handoff beat 5 within one sample in the synthetic `OfflineAudioContext` fixture.
- Both gain curves start and end at the same scheduled times.
- Cancellation stops stale sources and prevents audio from a prior generation.
- Offline peak remains below 0.98 with the chosen trims and master headroom.

### Perceptual handoff quality

Run five warmed and five cold trials on the acceptance device.

Definitions:

- **Cold:** page freshly loaded, track decoded, no prior handoff in the current page session.
- **Warmed:** at least one completed handoff in the current page session, followed by reset.

Pass requires:

- 10/10 technically complete handoffs without decode, suspension, scheduling, or stale-audio failure.
- At least 8/10 receive Tony's binary verdict **intentional** rather than **mechanical**.
- No missing or doubled audible beat from the final physical tap through handoff beat 9, subject to the ±60 ms tap-reconciliation rule.
- Trials include taps near both the low and high ±3 BPM boundaries; a perceptible tempo snap narrows the window before replication.
- No audible clipping in any accepted trial.
- A new tap during handoff cancels the old audio in all cancellation trials.

If perceptual acceptance fails, allow exactly one tuning cycle limited to percussion timbre, lead-in position, crossfade duration/curve, and target downbeat annotation. Rerun the same 10-trial protocol. If it still fails 8/10, stop and reassess rather than adding tracks.

### Licensing and privacy

- Bundled assets include a verifiable license source and required attribution.
- User-selected local files never leave the browser and are not persisted by the app.
- No copyrighted commercial track is committed or deployed without redistribution permission.

## Reviewer Concerns

The third and final allowed adversarial review did not return PASS. It found seven concrete implementation risks: a possible silent gap after the final tap, an unspecified estimated-to-track tempo snap, incomplete ownership of scheduled percussion nodes, insufficient track-tail validation, weak offline test oracles, missing output headroom, and ambiguity between Tone.js and native Web Audio.
