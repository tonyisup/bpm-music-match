## Problem Statement

Gate 1 proved that the tested Pixel 8 Pro and Android Chrome deployment can run one app-owned raw Web Audio graph, schedule phase-locked percussion and music, perform an equal-power overlapping handoff, stop cleanly, and terminate on foreground loss without stale audio.

That result removes the browser-control risk. It does not prove the product.

Milestone 2 must answer one narrower product question:

> When Tony manually taps a movement cadence, does the app lock that cadence and transform the taps into a real song in a way that feels musically intentional rather than mechanical?

The prototype remains a personal mobile-web experiment. It uses one exact local audio file selected from the phone. The file is decoded in browser memory, verified against manually curated metadata, and never uploaded or persisted. There is no provider, catalog, generalized matcher, account, backend, workout plan, or PWA shell.

## What Makes This Cool

The product moment is not “the app measured 120 BPM.” It is the realization that the song was hidden inside the user’s taps.

The intended sequence is sensory and causal:

1. Each physical tap receives immediate musical percussion feedback.
2. Stable tapping causes the app to become armed without falsely locking on noisy input.
3. Stopping is the confirmation gesture; no separate Lock button interrupts movement.
4. The rhythm continues without a missing beat while the app chooses a safe quantization boundary.
5. A real song enters on a curated downbeat and overlaps the percussion.
6. The percussion disappears while the song remains, making the transition feel inevitable.

The “whoa” is one continuous gesture becoming music, not a browse flow or a BPM result screen.

## Gate 1 Evidence Carried Forward

Gate 1 passed on:

- Pixel 8 Pro
- Android 16 build `CP1A.260505.005`
- Chrome `150.0.7871.181`
- tested/deployed commit `11df30f6f6cf90940bee425847614abaf26cc6f1`

The following contracts are proven enough to reuse as requirements and test patterns:

- one native `AudioContext` owns every source and gain path;
- first-gesture `resume()` remains inside the direct tap handler;
- audio scheduling occurs synchronously before the first `await`;
- sources have explicit generation ownership;
- scheduling is transactional and rolls back completely on partial failure;
- equal-power automation uses audio-clock scheduling, not DOM timers;
- manual cancellation holds the computed envelope value before ramping to zero;
- first terminal cause wins;
- stale callbacks and stale generations are no-ops;
- every generation termination clears source ownership; only application teardown closes the context;
- local diagnostics expose source counts, teardown settlement, context state, build identity, and typed errors.

Gate 1’s disposable UI and single-run application state are not product architecture and must not be promoted wholesale.

## Constraints

### Scope constraints

- One exact user-selected local track.
- One manually curated 1:1 track BPM.
- One manually curated clean 4/4 target-entry downbeat.
- One percussion character for the entire ten-trial protocol.
- One transition at a time.
- Stationary perceptual trials before any real-workout field trial.
- Raw Web Audio only; no Tone.js or media-element playback escape path.
- Static HTTPS deployment with no backend.

Explicitly excluded:

- YouTube Music, Spotify, Apple Music, or any provider integration;
- multiple tracks, catalog browsing, recommendation, generalized matching, or BPM discovery;
- half-time or double-time matching;
- automatic audio analysis, beat tracking, tempo extraction, or downbeat detection;
- accounts, analytics, remote logs, uploads, storage, service workers, offline installation, and PWA behavior;
- continuous motion sensing, heart-rate input, accelerometer input, workout programming, or background playback;
- time stretching, pitch shifting, normalization scans, dynamic limiting, or adaptive mastering.

### Local-track trust boundary

The local file is a controlled experimental fixture, not arbitrary user content.

Normative load order is:

```text
picker result
→ compressed byte-size check (reject above 20 MiB)
→ SHA-256 over raw bytes
→ reject immediately if SHA differs
→ decode only the known SHA-pinned bytes
→ validate observed decode properties against enrolled identity
→ bounded cue-energy validation
→ release every raw-byte reference
→ expose ready state
```

A wrong file is never decoded. Hash plus decode has a 15-second deadline. The fixture selects exactly one extension/MIME pair; Milestone 2 makes no generic compatibility claim.

Hard limits are 20 MiB compressed bytes, 360 seconds decoded duration, one or two decoded channels, decoded sample rate from 8–96 kHz, and calculated decoded PCM no greater than 160 MiB. Enrollment records exact decoded PCM as `audioBuffer.length × channels × 4`; `duration × sampleRate × channels × 4` remains a consistency estimate rather than the authority. Runtime accepts only the enrolled channel count, sample rate, duration within ±0.050 seconds, and exact PCM bytes.

Bounded validation checks 4,096 samples per channel at start and end plus the cue-energy window. It never scans the complete track. File path, raw filename, local URI, bytes, and audio content never enter diagnostics or persistent storage. The app uses no IndexedDB, Cache Storage, localStorage, service worker, upload, or remote request for the file. Reload requires selection again.

Run two consecutive cold load/unload cycles on the Pixel before trials. Require both to complete within limits, close their contexts successfully, and leave every application-owned raw-buffer, decoded-buffer, context, preview-source, and source-registry reference cleared. This is an application cleanup contract, not proof that Chrome released decoder/native/process memory.

Identity is split into exactly two evidence identities:

```text

  assetVersion
  displayLabel
  allowedExtension
  allowedMimeType
  sha256
  compressedBytes
```

The four application-memory fields are deliberately narrow. They prove fixed payload bounds and cleanup of references owned by this application. They do not claim browser-heap, decoder-native, or process-memory release because GitHub Pages JavaScript has no reliable cross-browser observation surface for those facts. Any later process-memory claim requires a separately versioned Pixel/DevTools protocol and must remain distinct from `assetIdentity`.

Every trial embeds both identities. Any permitted tuning change—including cue annotation, lead-in, match window, percussion, gain, crossfade duration, or curve—creates a new `configVersion`, a new deployment, and a complete protocol restart. The configured SHA is an identity, not a rights claim; private audio bytes never enter the repository.

A template is sufficient for design approval, but implementation planning remains blocked until local enrollment completes every field.

### Audio constraints

- The file must decode completely before tapping is enabled.
- The one owned `AudioContext` is constructed during accepted track loading. The first movement tap calls `resume()` under that direct gesture.
- The tap handler calls `resume()` without awaiting it, synchronously schedules the first acknowledgment, and only then crosses the first async boundary.
- Physical phase time and audible start time are distinct. The phase timestamp remains the mapped event time; an audible source uses the safety policy in the normative timing table.
- Exactly one pending resume effect is keyed by `{sessionId, generationId, effectId}`. Later taps in that generation reuse the pending promise and never call `resume()` again. If it rejects, scheduled sources roll back and application teardown reports `context-resume-failed`. If it resolves after its generation became stale, settlement immediately suspends the still-valid idle context; if application teardown began, settlement closes it. A stale resume can never leave an idle context running.
- All tap, predicted-percussion, track, and gain scheduling use the audio clock.
- UI timers can detect silence and update text but cannot execute source starts, gain transitions, or completion.
- The app schedules at most two predicted beats ahead while armed.
- Every predicted source has a stable source ID, scheduled audio time, generation ID, lifecycle state, and ownership role.
- Every generation cancellation holds computed gain values, ramps affected buses to zero over 20 ms, and stops sources at 25 ms.
- Foreground loss invalidates only the active generation, stops its sources, and suspends the context where possible. It preserves the decoded track for an explicit restart after return.

Three lifecycle levels are normative:

1. **Generation termination** cancels timers and sources for one tracking/handoff/playing attempt. It preserves the decoded track and owned context. Used by Reset, no-match cleanup, manual cancellation, and foreground loss.
2. **Session reset** performs generation termination and returns to `ready` with the decoded track and context retained. The next tap calls `resume()` again if needed. Used by warmed trials.
3. **Application teardown** performs generation termination, releases the decoded buffer, closes the context, and returns to `awaiting-track` or terminal reload recovery. Used by Unload Track, fatal setup/closed-context failure, replacement after explicit unload, pagehide, and reload.

A context that becomes `closed` unexpectedly cannot be reused. The app releases the decoded buffer and requires the file to be selected again. Gate 1's fresh-load terminal closure was spike-specific and is not silently applied to Milestone 2 warmed sessions.

### Product honesty constraints

- The UI distinguishes measured cadence from track BPM.
- A value outside the fixed window reports **No match in this one-track test**; it does not silently coerce any cadence into a match.
- “Intentional” versus “mechanical” is Tony’s binary perceptual judgment, recorded before detailed diagnostics are reviewed.
- A technically correct schedule cannot override an audible failure.
- One bounded tuning cycle is allowed. More tuning without new evidence is not progress.

## Premises

1. Milestone 2 tests stationary tap → lock → handoff quality, not full-workout usefulness.
2. One exact local track is the only match; there is no catalog or generalized matcher.
3. The disposable Gate 1 UI is not promoted into product architecture.
4. Raw Web Audio and Gate 1’s proven ownership/teardown contracts remain authoritative.
5. Ten stationary handoffs and one bounded tuning cycle decide whether the project proceeds to the field gate.
6. Provider integration remains blocked until the field gate passes.
7. Track tempo is a parameter. The edge-trial matrix is `trackBpm − 3`, `trackBpm`, and `trackBpm + 3`; 117/120/123 is valid only for a 120 BPM selected track.
8. A local-file flow is acceptable setup friction for a personal experiment because it isolates rights and provider constraints from the product interaction.

## Approaches Considered

### Approach A: Extend the disposable spike

Add file selection, tap estimation, and lock/handoff states directly to Gate 1’s modules.

**Effort:** Small
**Risk:** High

**Pros:**

- fastest path to a first audible tap sequence;
- reuses the existing page and deployment staging with minimal file churn.

**Cons:**

- preserves a single-use technical-test state model that was intentionally disposable;
- mixes product policy, diagnostics, browser lifecycle, and audio ownership in the same controller;
- makes repeated reseeding and deterministic replay harder to reason about;
- encourages accidental dependence on implementation details that Gate 1 never validated as product architecture.

**Decision:** Rejected.

### Approach B: New deterministic vertical slice

Create a new static product surface around pure tap-estimation, handoff-planning, and session-reduction modules. Keep browser file access, Web Audio, timers, and DOM rendering behind adapters. Reuse Gate 1 invariants and selected low-level math, not its application shape.

**Effort:** Medium
**Risk:** Low–medium

**Pros:**

- timestamp sequences can be replayed deterministically without a browser or phone;
- product policy is inspectable independently from Web Audio mechanics;
- the adapter boundary supports fake audio, synthetic offline rendering, and the real Android browser with the same plans;
- repeated cadence reseeding has an explicit generation transition rather than an improvised reset;
- failures can be assigned to estimator, planner, engine, local-file loader, or UI rather than collapsed into “the demo felt wrong.”

**Cons:**

- requires explicit contracts before the first audible demo;
- creates more files and tests than mutating the spike.

**Decision:** Chosen.

### Approach C: Full workout/PWA shell

Build installation, persistence, session history, multiple-track flows, offline support, and repeated workout transitions around the vertical slice immediately.

**Effort:** Large
**Risk:** High

**Pros:**

- visually resembles an eventual product;
- could reduce repeated setup if persistence were later justified.

**Cons:**

- tests several unrelated hypotheses simultaneously;
- service-worker and cache behavior complicate build, file, and metadata identity;
- spends architecture before the handoff has demonstrated product value;
- creates pressure to add provider/catalog work to justify the shell.

**Decision:** Rejected.

### Tap estimator

Input is the latest accepted monotonic tap timestamps in milliseconds. The timestamp window retains at most eight accepted taps. Repeated, decreasing, non-finite, too-future, or too-late events are rejected before insertion. A range-invalid interval rejects only that interval; both endpoint taps remain in the window and can form neighboring intervals.

Median is normative: sort finite values ascending; odd count selects the middle; even count is the arithmetic mean of the two middle values.

```text
window = latest at most 8 accepted taps
rawIntervals = adjacent differences in window
rangeEligible = intervals where 250 <= intervalMs <= 2000
seedMedian = median(rangeEligible)
valid = rangeEligible where abs(intervalMs - seedMedian) / seedMedian <= 0.20
stableMedian = median(valid)
mean = arithmetic mean(valid)
populationStdDev = sqrt(sum((x - mean)^2) / count(valid))
coefficientOfVariation = populationStdDev / mean
armed = count(valid) >= 4 and coefficientOfVariation <= 0.05
estimatedBpmExact = 60000 / stableMedian
estimatedBpmDisplay = round estimatedBpmExact to nearest integer, ties away from zero
silenceTimeoutMs = clamp(1.5 * stableMedian, 900, 1800)
```

The rejection pass is single-pass; rejected intervals do not trigger recomputation. Equality at 20% is accepted and equality at 5% CV is stable. Matching uses the unrounded double.

Every accepted tap starts an idle deadline. Before `stableMedian` exists, it is a fixed 1,800 ms bootstrap deadline. Once a stable median exists, it uses the formula above. Silence while non-armed always terminates the generation and returns `ready`; one-tap and non-estimable attempts therefore cannot hang.

### Clock mapping

At tap handling, sample `performance.now()` and `AudioContext.currentTime`:

```text
mappedTapAudioTime = audioNow + (eventTimestampMs - performanceNowMs) / 1000
```

| Constant/policy | Value |
|---|---:|
| event timestamp future tolerance | 16 ms |
| maximum accepted event lateness | 100 ms |
| running-context audible safety offset | 5 ms |
| suspended/first-tap scheduling lead | 20 ms |
| complete handoff transaction lookahead | 100 ms |
| predicted-hit reconciliation tolerance | ±60 ms inclusive |
| BPM match window | `abs(estimatedBpmExact - trackBpm) <= 3.0` inclusive |
| maximum grid catch-up / delayed-lock skips | 2 whole beats |
| startup/resume deadline | 1,000 ms |

A timestamp over 16 ms future or 100 ms past is invalid and is not inserted into estimator state. If such an event occurs during tracking/armed, the generation terminates to `ready`; the UI does not build a phase grid from stale time.

For a valid event, physical phase remains mapped time. Audible start is `max(mappedTapAudioTime, audioNow + 0.005)` when running, otherwise `audioNow + 0.020`. The source is scheduled synchronously before awaiting the tokenized resume effect.

Subsequent future-grid calculation advances from physical phase by whole estimated periods until the first beat is at least `audioNow + 0.100`. More than two advances terminates with `tap-grid-too-late`.

Events are reduced serially. The lock deadline is one atomic reducer event: it snapshots estimator, clock, and source registry and returns `no-match`, `handoff`, or `error` directly—there is no intermediate `locked` state. A tap reduced first refreshes cadence; a tap reduced after `handoff` is cancellation. Exact timestamp equality does not override queue order.

### Session reducer

The pure reducer consumes one event and returns immutable state plus ordered effects. There is no browser-only intermediate lock state.

| State | Event | Next state | Ordered effects / retained data |
|---|---|---|---|
| `awaiting-track` | choose/file/cancel/load result | `selecting-track`, `loading-track`, `ready`, or `awaiting-track` | enforce tokenized load and application teardown on cancel/failure |
| `ready` | valid tap | `tracking` | new generation; tokenized resume; synchronous acknowledgment; bootstrap deadline |
| `tracking` | valid tap | `tracking` or `armed` | recompute; acknowledge; start predictions only if armed; refresh deadline |
| `tracking` | idle deadline | `ready` | generation termination; retain loaded session |
| `armed` | valid tap, estimator remains stable | `armed` | reconcile; update grid; refresh deadline |
| `armed` | valid tap destabilizes estimator | `tracking` | cancel every not-started prediction; acknowledge/re-anchor; bootstrap/formula deadline |
| `armed` | atomic lock deadline | `no-match`, `handoff`, or `error` | freeze exact estimator; classify; construct/commit one complete source plan or terminate |
| `no-match` | Try again with attempts remaining | `ready` | append cadence-unqualified attempt; retain decoded session and cold/warmed classification |
| `no-match` | third no-match in slot | `evidence-pending` | score slot failure; freeze attempts array |
| `handoff` | song-only boundary | `playing` | percussion ownership ends |
| `playing` | End trial after beat 9 | `cancelling` | accepted `trial-complete` cause; click-free track stop; not a defect |
| `handoff`/`playing` | tap or Reset | `cancelling` | generation termination; do not reuse tap |
| `cancelling` | teardown settled | `evidence-pending` | freeze sanitized trial report |
| `playing` | natural end | `evidence-pending` | clear track ownership; freeze report |
| any active state after first accepted tap | technical failure/effect-failed | `terminating-failure` | first cause wins; freeze sanitized report and paired-warm auto-failure before resource teardown |
| `terminating-failure` | teardown settles or itself fails | `evidence-pending` | append cleanup result; retain report even when buffer/context were released |
| active state | hidden/suspended | `interrupted` | first cause wins; freeze report; terminate generation; tokenized resume settlement must suspend |
| `interrupted` | foreground restored or teardown settles | `evidence-pending` | no automatic audio; retain report independently of audio resources |
| `evidence-pending` | evidence downloaded + verdict recorded | terminal result state | mark evidence resolved; enable resource-appropriate Reset/Choose/Reload |
| any loaded terminal state | Reset | `ready` | only legal after evidence resolution and when decoded session survived |
| any loaded state | Unload Track | `awaiting-track` | application teardown |
| loaded state before first tap | unexpected closed context/fatal setup | `error` | application teardown; no trial evidence exists |
| active state after first tap | unexpected closed context | `terminating-failure` | freeze report first; application teardown second |
| any state | stale token/generation callback | unchanged | no effects; diagnostic only |

`effect-failed` carries `{sessionId,generationId,effectId,effectType,cause}` and is legal from any state owning that pending effect. Resume failures map to `context-resume-failed`; plan/source/gain failures map to `schedule-failed`. A stale resume rejection is a diagnostic-only no-op; stale success follows the suspend/close rule. Neither can replace the first cause. Invalid events are no-ops unless timing policy explicitly requires safe generation termination.

Loading offers Cancel, not replacement. A new file appears only after Unload/application teardown, preventing simultaneous decoded sessions.

### Predicted percussion reconciliation

While unstable, each valid physical tap schedules one immediate hit. Once armed, at most two future predicted hits are owned.

A predicted source's lifecycle is derived, not callback-based:

```text
notStarted := scheduledAudioTime > audioNow + oneSampleDuration
startedOrDue := not notStarted
ended := onended observed
```

At physical taps, ±60 ms inclusive reconciliation avoids duplicates; outside tolerance, all not-started predictions are cancelled and a safe-future grid is rebuilt with the two-skip rule.

At atomic lock, the planner first chooses `handoffBeat1AudioTime >= audioNow + 0.100`. Any prediction before beat 1 remains a documented `bridge` beat and is not part of the handoff. For each predicted source at or after beat 1:

- if its time equals one of handoff beats 1–8 within one decoded output sample, put it in `adoptedSourceIdsByBeat[beatIndex]`;
- otherwise put it in `cancelSourceIds`.

The plan enumerates every currently owned predicted source exactly once as bridge, adopted, or cancelled. Before commit, the engine verifies set equality with the ownership snapshot, cancels every `cancelSourceId`, preserves bridge sources, and schedules only handoff beat indexes absent from `adoptedSourceIdsByBeat`. It never schedules a duplicate for an adopted beat.

The 100 ms lookahead applies to the complete transaction even when beat 1 was pre-scheduled. A source closer than 100 ms cannot become beat 1; it becomes bridge if still future/due, and the planner advances to the next grid beat. More than two advances fails.

Commit allocates and validates track source, missing percussion, gains, and automation before changing bookkeeping roles. If allocation/scheduling fails, the entire generation terminates; it does not attempt to restore a rolling prediction state. Tests cover two simultaneous predictions, just-before-start classification, bridge+adopt, adopted beat 1/2, unaligned cancellation, and snapshot set mismatch.

### Silence lock and handoff planning

The lock timer dispatches one atomic `lock-deadline` event; it never starts audio. The reducer snapshots estimator, clock, and source registry, applies the inclusive ±3 BPM match, and either returns `no-match` or consumes one validated immutable plan to enter `handoff`.

Normative plan fields include generation ID; both evidence identities; full-precision estimated/track/snap BPM; last tap; timer deadline/lateness; skipped-beat count 0–2; beat-1 time; `bridgeSourceIds`; `adoptedSourceIdsByBeat`; `cancelSourceIds`; exactly eight increasing beat times; track start/offset; beat-4 fade start; beat-5 cue time; beat-8 fade end; trims; and exact continuation bounds:

```text
minimumRequiredAudioEndTime = crossfadeEndAudioTime + minimumPostCrossfadeTailSeconds
naturalTrackEndAudioTime = trackStartAudioTime + (decodedDurationSeconds - trackStartOffsetSeconds)
naturalTrackEndAudioTime >= minimumRequiredAudioEndTime
```

`technically complete` means one committed plan, `playing` reached, beat 9 song-only reached, no typed defect/stale side effect, and expected ownership settled. Plan and snapshot validation occurs before commit; any failure terminates the generation as `schedule-failed`.

### Handoff audio graph

The graph remains:

```text
percussion source → percussion trim → percussion crossfade gain \
                                                              → master gain → destination
track source      → track trim      → track crossfade gain      /
```

For 4/4:

- percussion handoff beats are numbered 1–8;
- track source begins at handoff beat 1 using the curated four-beat pre-roll offset;
- track gain remains zero through beat 3;
- the four-beat equal-power fade starts exactly at beat 4;
- the curated song downbeat reaches output at beat 5, one beat into the fade, where theoretical music gain is `sin(π/8) ≈ 0.3827` rather than zero;
- the fade ends exactly at beat 8;
- percussion ownership ends after beat 8;
- beat 9 begins song-only playback.

This resolves the product statement “song enters on a curated downbeat”: the song may emerge quietly during beat 4, but the curated beat-5 downbeat must have audible energy. The offline oracle asserts both timestamp alignment and a nonzero energy window around the target transient.

Timing invariant:

```text
beatDurationSeconds = 60 / handoffBpm
trackStartOffsetSeconds = targetEntryDownbeatSeconds - 4 * beatDurationSeconds
trackStartAudioTime = handoffBeat1AudioTime
curatedDownbeatAudioTime = handoffBeat1AudioTime + 4 * beatDurationSeconds
crossfadeStartAudioTime = handoffBeat1AudioTime + 3 * beatDurationSeconds
crossfadeEndAudioTime = handoffBeat1AudioTime + 7 * beatDurationSeconds

0 <= trackStartOffsetSeconds
targetEntryDownbeatSeconds + 3 * beatDurationSeconds
  + minimumPostCrossfadeTailSeconds <= decodedTrackDurationSeconds
```

Use paired 128-sample curves from angle 0 to π/2 over beat 4 through beat 8. At the beat-5 downbeat, normalized curve progress is 0.25.

Private-fixture cue validation runs only during local enrollment/runtime: inspect decoded samples from the cue timestamp through +50 ms across all channels; compute RMS as `sqrt(sum(sample²) / totalSamples)` and peak as maximum absolute sample; require RMS ≥ 0.010 and peak ≥ 0.050 before gains. Failure means the annotation/file is unsuitable. Synthetic offline tests verify timing and gain math only.

### Reseeding

Seamless same-tap reseeding is deferred to the field gate.

For Milestone 2, a tap during `handoff` or `playing` is a safety cancellation signal only. It invalidates the old generation, holds/ramp-stops old audio, settles teardown, and returns to `ready`. The cancelling tap is not retained and cannot schedule new-generation audio. The user must tap again to begin a new sequence.

The two real-device cancellation smokes validate click-free cancellation and stale-source prevention. They do not claim a workout-ready reseeding interaction. The field-gate design must separately decide whether and how a cancellation tap can also become the first tap of the next cadence.

### UI and accessibility

The mobile surface contains only Choose Track, one large semantic tap button, configured non-sensitive label/BPM, status/instructions, tentative measured BPM while armed, locked/track BPM during handoff, one recovery control, and collapsed diagnostics.

State/control matrix:

| State | Primary control | Announcement | Retained data / focus |
|---|---|---|---|
| `awaiting-track` | Choose track | “Choose the configured test track.” | no bytes/buffer/context; focus remains Choose track |
| `selecting-track` | picker owned by OS | none beyond picker | no bytes retained on cancel |
| `loading-track` | Cancel loading | “Validating track.” | transient bytes/context only; Cancel returns awaiting-track and focus to Choose track |
| `ready` | Tap movement | “Ready. Tap your movement, then stop.” | decoded buffer/context/identities retained; focus tap control |
| `tracking` | Tap movement | no per-beat live announcement | taps/active generation retained |
| `armed` | Tap movement | announce tentative BPM and “Stop tapping to lock” once | predicted registry retained; pulse is aria-hidden |
| `no-match` | Try again, or evidence after third no-match | “No match in this one-track test.” | decoded session retained; focus sole available action |
| `handoff` | Cancel | announce “Handoff started” once | decoded session + active generation |
| `playing` | End trial | announce track label and BPM once | enabled only after beat 9; decoded session + active track |
| `cancelling` | disabled | “Stopping.” | decoded session retained; settlement enters evidence-pending |
| `interrupted` | disabled until foreground return | “Audio stopped when the page left the foreground.” | decoded session retained; foreground return enters evidence-pending |
| `evidence-pending` | Record verdict, then Download trial evidence | announce result once | Reset/Unload disabled until download gesture resolves evidence |
| pre-tap `error` | Choose track again or Reload | typed human-readable setup failure | no trial evidence exists; application teardown |
| post-tap `terminating-failure` | disabled while teardown settles | announce first failure once | sanitized report retained independently from audio resources |
| natural track end | Record verdict, then Download evidence | “Track complete.” | decoded session retained; enters evidence-pending |
| post-tap fatal/closed context | Record `not-judged`, then Download evidence | single failure announcement | application teardown may release audio, never report |

There is no replacement-file control while decode or a loaded session is active. **Unload Track** appears as a secondary control in `ready`, resolved terminal result, and pre-tap recoverable-error states only; it is hidden during active audio and evidence-pending. It performs application teardown before exposing Choose Track.

`evidence-pending` prevents silent evidence loss. The subjective control offers `intentional`, `mechanical`, and `not-judged` (only when no audible handoff occurred). Download stays disabled until a verdict is selected. Reset, Choose Track, Reload, and Unload stay disabled until the download gesture completes. Navigation triggers a warning; if the user leaves anyway, the external worksheet marks the slot `evidence-missing`, which is a technical failure.

After evidence resolves, recovery depends on retained resources: a valid loaded session enables Reset to `ready`; an application-teardown failure enables Choose Track again or Reload. Evidence ownership is independent of `AudioBuffer`, `AudioContext`, source registries, and raw bytes.

Every visual pulse is `aria-hidden` and disabled under `prefers-reduced-motion`. Timed beat/crossfade labels do not enter a live region. State changes are announced once. Focus moves only when a transition disables the currently focused control.

Perceptual trials are listening-first: Tony records intentional/mechanical and audible defects before expanding diagnostics.

## Failure Contract

The first accepted terminal cause owns one generation. Later cleanup failures append diagnostics but cannot replace the product cause or leave settlement pending.

| Code | Definition | Lifecycle scope | Recovery |
|---|---|---|---|
| `track-selection-cancelled` | OS picker returns no file | none | `awaiting-track`; Choose Track |
| `track-read-failed` | selected bytes cannot be read or exceed 20 MiB | application teardown | Choose Track again |
| `track-identity-failed` | SHA-256 differs from immutable stimulus SHA | application teardown | Choose Track again |
| `track-metadata-invalid` | schema, MIME/extension, BPM, timing, or limits invalid | application teardown | fix deployment metadata; Reload |
| `track-decode-failed` | decode rejects or hash+decode exceeds 15 seconds | application teardown | Choose Track again; record browser/format |
| `track-bounds-invalid` | decoded duration/channels/rate/PCM estimate/downbeat bounds fail | application teardown | Choose Track again or fix metadata |
| `context-resume-failed` | direct-gesture `resume()` rejects | freeze report, then application teardown after source rollback | evidence, then Choose Track again/Reload |
| `tap-timestamp-invalid` | timestamp non-finite, >16 ms future, >100 ms past, repeated, or decreasing | generation continues only if ownership is safe; otherwise terminate | evidence when terminal, then Reset |
| `tap-grid-too-late` | delayed valid tap requires >2 period advances to create a safe future grid | generation termination | evidence then Reset; trial fails technically |
| `lock-timer-too-late` | atomic lock requires >2 grid advances to create a 100 ms transaction window | generation termination | evidence then Reset; trial fails technically |
| `schedule-failed` | immutable plan or ownership transaction cannot commit | freeze report, then generation termination | evidence then Reset; trial fails technically |
| `startup-timeout` | within 1,000 ms of first tap the context never reaches running with the first source owned at a future/started time and advancing audio clock | freeze report, then application teardown | evidence, then Choose Track again/Reload |
| `runtime-context-interrupted` | hidden/suspended state wins while generation active | freeze report, generation termination, attempted suspend | foreground return, then evidence |
| `runtime-context-closed` | owned context closes unexpectedly | freeze report, then application teardown | evidence, then Choose Track again/Reload |
| `context-close-failed` | application teardown close rejects or remains unsettled after 1,000 ms | append cleanup failure to frozen report | evidence, then Reload |

`no-match` is an expected product result, not an error. `trial-complete` after the user activates End trial at or after beat 9 is also not an error. It performs the standard click-free stop and enters evidence-pending. Natural track completion follows the same evidence path.

Normative evidence-before-resources rule: after a slot's first accepted tap, every terminal event first freezes a sanitized in-memory report—including an auto-failed paired warmed slot when applicable—and only then performs generation or application teardown. Teardown may release the decoded buffer and context but cannot clear or replace the report. Teardown failure appends to that report and still enters `evidence-pending`. Choose Track, Reload, Reset, and Unload remain unavailable until verdict and download resolve evidence.

A loading Reset marks the load token stale, prevents any late hash/decode result from attaching state, releases available buffers, closes the context, and returns to `awaiting-track`. Replacement selection is unavailable until application teardown completes.

Recovery remains singular in every rendered state; the UI never presents competing Reset/Reload/Choose actions.

## Deterministic Verification

### Pure estimator tests

Center qualification on the selected stimulus BPM `B`, not a speculative general-purpose range:

- steady sequences near `B`, `B − 3`, and `B + 3` estimate within ±0.5 BPM;
- exact inclusive match boundaries at `B ± 3.0` pass;
- `B ± 3.0001` does not match;
- fewer than four valid intervals cannot arm;
- exact 20% interval deviation is retained and just above is rejected;
- exact population CV 5% arms and just above does not;
- one delayed interval recovers under the single-pass median rule;
- silence timeout formula and 900/1,800 ms clamps;
- 250/2,000 ms interval bounds and just-outside values;
- non-finite, repeated, decreasing, and >16 ms future timestamps;
- matching uses unrounded BPM while display rounding is isolated.

Broader 60–180 BPM qualification is deferred until the estimator becomes reusable product scope.

### Reducer and replay tests

Replay fixtures feed timestamp/event sequences and assert complete ordered traces: states, estimator snapshots, silence deadlines, predicted-source roles, lock ownership snapshot, immutable handoff plan, generation changes, ordered effects, and terminal diagnostics.

Required fixtures:

- stable center and both inclusive edge classes;
- just-outside-window no-match;
- jitter/outlier recovery;
- silence while unstable;
- tap processed immediately before lock deadline;
- lock processed before a concurrent tap;
- armed tap destabilizes back to tracking;
- two owned predictions are exhaustively classified as bridge/adopted/cancelled;
- a prediction inside 100 ms becomes bridge, never beat 1;
- adopted beat 1 and beat 2 are not rescheduled;
- just-before-start lifecycle derives from current time and one sample;
- zero/one/two grid advances and more-than-two failure;
- cancellation during handoff and playing returns to `ready` without reusing the cancelling tap;
- visibility/context interruption first-cause races;
- resume failure, unexpected close, and teardown failure freeze evidence before releasing application resources;
- natural end, End trial, interruption, and fatal failure all converge on evidence-pending;
- stale load/effect/source callbacks.

Replay is a test harness, not a user-facing product surface.

### Offline audio tests

Use synthetic impulses and pulse trains, never the private local track, to verify:

- handoff beat 1 and each of eight percussion times within one rendered sample;
- target downbeat lands at beat 5 within one rendered sample;
- crossfade starts at beat 4 and ends at beat 8;
- target-downbeat synthetic output window has nonzero music energy at theoretical gain `sin(π/8)`;
- 128 paired equal-power samples are finite and monotonic;
- `musicGain² + percussionGain² ≈ 1` over the crossfade;
- peak remains below 0.98 with configured trims;
- cancellation uses held computed values and old generation is silent after cutoff;
- natural and intentional `onended` paths remain distinct.

The actual SHA-pinned fixture receives browser/local enrollment validation over exact start/end 4,096-sample windows and the cue-to-+50 ms RMS/peak oracle; it is never copied into offline tests.

### Browser contract tests

Fake File, SubtleCrypto, AudioContext, DOM, visibility, and timers to prove:

- local bytes never leave the process;
- compressed, duration, channel, sample-rate, and estimated-PCM limits fail before unsafe retention;
- raw bytes are dereferenced after hash/decode settlement;
- wrong SHA prevents accepted decode/readiness;
- MIME/extension and decoded bounds are validated after context-driven resampling;
- direct-tap ordering calls one tokenized resume, schedules before first await, shares pending resume across later taps, rolls back on rejection, suspends on stale success, and closes on success after teardown;
- adopted predicted sources cannot be double-scheduled at any handoff beat;
- Reset preserves decoded session while Unload performs application teardown;
- foreground loss clears generation ownership but preserves loaded session;
- post-tap application teardown releases audio resources without clearing the sanitized report;
- evidence-pending blocks Reset, Choose, Reload, and Unload until verdict plus download;
- stale callbacks cannot mutate the active generation;
- diagnostics omit filename, path, URI, and bytes;
- user-initiated evidence export contains only the sanitized schema;
- HTML and executable module build identities agree.

## Real-Device Acceptance Protocol

Use the same Pixel 8 Pro, Android 16, and Chrome family that passed Gate 1 unless a documented device change is intentional. Let `B = configured track BPM`; classification uses frozen unrounded `estimatedBpmExact`.

Normative trial classes:

```text
CENTER: B - 0.75 <= estimate <= B + 0.75
LOW_EDGE: B - 3.00 <= estimate <= B - 2.25
HIGH_EDGE: B + 2.25 <= estimate <= B + 3.00
```

Every boundary is inclusive. Estimates in the gaps are valid app inputs but do not qualify for the assigned protocol slot. Estimates outside `B ± 3.00` must produce `no-match` and likewise do not qualify for that handoff slot.

Run five fixed page sessions, each containing one cold slot followed by one warmed slot:

| Session | Cold slot | Warmed slot |
|---:|---|---|
| 1 | CENTER | LOW_EDGE |
| 2 | HIGH_EDGE | CENTER |
| 3 | LOW_EDGE | HIGH_EDGE |
| 4 | CENTER | LOW_EDGE |
| 5 | HIGH_EDGE | CENTER |

Totals are four CENTER, three LOW_EDGE, three HIGH_EDGE; five cold and five warmed. Fixed order is deliberate and reproducible. No post-hoc replacement or cherry-picking is allowed.

Definitions:

- **Cold:** fresh page load, one successful local selection/decode, no prior handoff in that page session.
- **Warmed:** the immediately following slot after the cold trial reaches terminal settlement and Reset retains the same decoded session.
- **Attempt begins:** first accepted physical tap after the slot is declared.
- **Scored trial:** the first attempt whose frozen estimate lands in the assigned class, or the slot's terminal failed attempt under the rules below.

Retry/denominator rules:

1. Picker cancellation before the first accepted tap is setup and does not start a slot.
2. A cadence attempt that cleanly reaches pre-handoff `no-match` is logged as `cadence-unqualified`; it may be retried at most twice because no prior handoff changes cold/warmed classification.
3. If three attempts fail to enter the assigned class, the slot is recorded as one scored technical failure. The protocol continues; the ten-slot denominator remains ten.
4. Any app error, missing/double beat, click, gap, clipping, stale audio, ownership leak, or teardown failure after the first tap immediately becomes the slot's scored failure. It cannot be retried away.
5. A handoff whose frozen estimate is outside the assigned protocol class is the slot's scored technical failure even if it is inside the app's ±3 BPM match window. It cannot be retried because a handoff occurred and changed session history.
6. A class-valid attempt is the scored trial whether it feels intentional or mechanical. No second take replaces it.
7. Reload during an active slot is a scored failure unless forced by a previously scored terminal app failure.
8. If a cold scored failure performs application teardown, its paired warmed slot is automatically recorded as `paired-session-unavailable`, `technicalPass=false`, `subjectiveVerdict=not-judged`; no replacement load may be mislabeled warmed. Continue with the next numbered fresh session.
9. A technical failure before audible handoff uses `not-judged`; it cannot count toward the 8 intentional trials.

Evidence capture is explicit but non-automatic:

- The app keeps only the current sanitized trial report in memory.
- At terminal settlement, Tony records **intentional** or **mechanical**; `not-judged` is allowed only when technical failure prevented an audible handoff. Detailed diagnostics remain locked until selection.
- A direct **Download trial evidence** gesture saves one sanitized JSON file. This user-directed export is the evidence artifact; the app itself has no persistent store.
- Cold evidence must be downloaded before Reset/warmed trial. If its failure destroyed the session, the same export also contains the auto-failed paired warmed slot. A download omission is `evidence-missing` and fails the affected slot(s).
- The JSON includes build, asset and experiment-config identities; session/slot IDs; an `attempts[]` array containing every cadence-unqualified and scored attempt; assigned and actual class; tap timestamps relative to each attempt’s first tap; estimator data; resume/lock/timer/source-classification decisions; immutable handoff plan; source/teardown summary; technical verdict; subjective verdict (`intentional`, `mechanical`, or `not-judged`); and defect flags.
- It excludes local filename, path, URI, absolute wall-clock location data, bytes, and audio content.
- A screenshot is supporting evidence only; JSON is the reproducible record.

A slot is technically complete only under the normative plan definition: single commit, `playing` reached, beat 9 song-only reached, no defect/failure/stale side effect, and expected ownership settled.

Pass requires:

1. 10/10 technically complete scored handoffs.
2. At least 8/10 scored handoffs judged **intentional**.
3. No missing or doubled audible beat from final physical tap through beat 9.
4. No audible clipping, click, gap, or stale-generation audio.
5. LOW_EDGE and HIGH_EDGE results explicitly adjudicate whether the tempo snap feels mechanical.
6. All source/teardown records settle without stale ownership.

After ten slots, run two separate cancellation smokes that are not part of the 8/10 denominator:

- one tap during crossfade;
- one tap during playing.

Each cancelling tap must stop the old generation without a click, delayed tail, double acknowledgment, or stale restart, then return to `ready`. The next tap—not the cancelling tap—must begin the next generation.

### Bounded tuning cycle

If fewer than 8/10 handoffs feel intentional, allow exactly one tuning cycle limited to:

- percussion timbre;
- target-entry downbeat annotation;
- lead-in position;
- crossfade duration/curve;
- fixed percussion, track, and master trims;
- fixed acceptance window only when edge-trial tempo snap is the diagnosed cause.

Every change is versioned, verified, redeployed, identity-checked, and followed by the entire ten-trial protocol. If the second protocol still fails, stop and reassess the interaction. Do not add tracks, providers, personalization, or UI polish to conceal a weak handoff.
